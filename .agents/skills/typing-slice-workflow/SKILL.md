# 이슈 기반 슬라이스 진행

사용자 기능·버그 수정처럼 리뷰 가능한 변경을 구현하거나 진행 중인 작업을 이어받을 때 사용한다. 단순 오탈자 수정은 저장소 지침에 따라 처리한다.

## 작업 상태와 계약

- 작업 범위와 완료 조건의 원본은 사용자 요청과 GitHub 이슈다. 이슈 체크리스트가 있으면 진행 중 근거를 PR에 남기고 완료 시 최신 상태로 갱신한다.
- 현재 제품 동작의 권위 문서는 [docs/PROJECT-SPEC.md](../../../docs/PROJECT-SPEC.md)다. 변경이 사용자에게 보이는 계약을 바꿀 때만 이를 갱신한다.
- Draft PR은 구현 개요, 이유, 완료 조건, 확인 범위를 보관한다. 한 번만 수행한 검증과 미확인 플랫폼은 PR 또는 [플랫폼 검증표](../../../docs/PLATFORM-VERIFICATION.md)에 남긴다.
- 진행 중인 작업을 찾을 때는 같은 이슈의 기존 PR을 이어 쓴다. 현재 브랜치, 작업 트리, 연결 PR, 최신 `main`을 먼저 확인한다.

## 진행 순서

1. 명시된 이슈나 사용자 요청을 선택하고, 현재 동작·제약·완료할 사용자 행동을 확인한다. 계획이 바뀌면 이슈와 해당 제품 계약을 함께 맞춘다.
2. 새 슬라이스는 최신 `main`에서 `codex/` 임시 브랜치로 시작한다. 첫 의미 있는 변경을 커밋·푸시한 뒤 `main` 대상 Draft PR을 열고 이슈, 범위, 접근, 완료 조건을 기록한다.
3. 동작 단위로 커밋하고 같은 브랜치에 푸시한다. 실제 코드·런타임 동작을 바꿀 때 관련 검증을 수행한다. 문서 전용 변경은 앱 테스트·빌드·CI 대신 링크, 명세, 참조, 메타데이터, 고지를 점검한다.
4. 완료 조건이 충족되면 이슈 체크리스트를 갱신하고 짧게 해결 내용을 댓글로 남긴다. 영향받은 명세·안내·아키텍처·플랫폼·변경 이력만 정렬한다. 미확인 사항은 실패로 꾸미지 않고 필요한 환경과 함께 증거 공백으로 적는다.
5. 최종 변경과 PR 설명을 맞추고 저장소의 필수 리뷰·체크 조건을 따른다. 병합이 허용되면 `main`에 병합하고 확인한 뒤 임시 로컬·원격 브랜치를 삭제한다. 체크나 권한이 실제로 막으면 PR과 브랜치를 유지하고 재개에 필요한 조건을 기록한다.

## 버전과 릴리즈

문서 전용 변경은 버전을 올리지 않고 태그나 릴리즈를 만들지 않는다. 작은 사용자 기능은 마지막 버전 자리를, 누적된 사용자 경험 변경은 두 번째 자리를 올리는 기존 정책을 따른다. 버전을 올리는 사용자 변경에서는 앱 메타데이터와 CHANGELOG를 맞추고 별도 승인 대기 없이 해당 이슈의 릴리즈 절차를 끝까지 진행한다.

## 검토 기준

PR 완료 전 변경이 이슈 범위와 일치하는지, 사용자 동작을 바꿨다면 명세가 같은 동작을 설명하는지, 해당 문서의 링크와 사실이 유효한지 확인한다. 코드·버전·릴리즈를 다루지 않은 문서 작업에서 이를 모두 갱신하도록 강제하지 않는다.
